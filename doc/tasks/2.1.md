# 任务 2.1：底盘控制与 odom 闭环验证

状态：已规划，待执行

## 1. 为什么做

导航的地基是「可控的底盘」和「可信的里程计」。阶段 1 只验证了轮子能转，没验证 cmd_vel 接口实况和 odom 精度。2.1 在动传感器、建图之前先把这两块摸清并量化，避免 2.4 接入 nav2 时才发现接口对不上。

## 2. 在整机项目中的作用

移动基座闭环。nav2 的 `controller_server` 输出速度指令，经 `diff_drive_controller` 驱动轮子；`/odom` 供 slam_toolbox/AMCL 做位姿估计。2.1 保证「指令 → 运动 → 里程计」链路闭环且可量化。

## 3. 输入

- 阶段 1 整机 + ros2_control（`diff_drive_controller` active）。
- `config/biadapt_controller.yaml`（diff_drive_controller 的 cmd_vel 订阅话题名与消息类型由源码硬编码，不在该 YAML 里配置；见步骤 1）。
- 已知历史踩坑点（阶段 1 已验证）：wheel_separation 必须等于实际轮距；cmd_vel 话题名不对齐导致收不到指令；cmd_vel_timeout 过短导致走走停停。

## 4. 输出

- cmd_vel 接口现状确认：实测 diff_drive_controller 的订阅话题与消息类型，并给出 2.4 接入 nav2 时的对齐方案。
- 用正确话题和消息类型发指令，底盘能前进与原地转。
- `odom → base_footprint` TF 正确存在。
- 量化记录：直线走 1m 的 odom 实测位移误差、原地转 90° 的实测航向误差。

## 5. 边界与风险

- 只做底盘闭环，不做建图、不做导航、不动传感器。nav2 与 diff_drive_controller 的 remap 对齐在 2.4 落地，2.1 只确认现状并验证。
- 风险 a：cmd_vel 话题名选错（两边话题名不一致），nav2 或手动指令底盘收不到。
- 风险 b：odom 漂移大（wheel_separation 不符、轮子打滑、无 IMU）。
- 风险 c：纯仿真里量 1m 距离需要参照物，不能用真卷尺。

## 6. 验收方式（可复现）

1. `ros2 topic pub -r 10 /diff_drive_controller/cmd_vel geometry_msgs/msg/TwistStamped "{twist: {linear: {x: 0.2}}}"` 后底盘前进；换 `twist.angular.z` 后底盘原地转。
2. `ros2 topic info /diff_drive_controller/cmd_vel -v` 显示 diff_drive_controller 为订阅者、消息类型为 `geometry_msgs/msg/TwistStamped`。
3. `ros2 run tf2_echo odom base_footprint` 有输出；`view_frames` 显示 `odom → base_footprint` 边，发布者是 `diff_drive_controller`。
4. 直线走 1m：odom 位移误差 ≤ 5%（记录实测值）。
5. 原地转 90°：odom 航向误差 ≤ 5°（记录实测值）。

## 7. 详细步骤（接口给名称与用途，不写完整实现）

### 步骤 1：确认 cmd_vel 接口现状

依据本机源码，两边的事实是：

- `diff_drive_controller`（`/home/code-robot/ros2_controllers/diff_drive_controller/`）：
  - 订阅话题名是源码常量 `DEFAULT_COMMAND_TOPIC = "~/cmd_vel"`（`diff_drive_controller.cpp`），解析为 `/diff_drive_controller/cmd_vel`。
  - 消息类型在源码里硬编码为 `geometry_msgs/msg/TwistStamped`。
  - 参数文件 `diff_drive_controller_parameter.yaml` 里没有 cmd_vel 话题名或消息类型参数。
- nav2 的 `controller_server`（`/home/code-robot/navigation2/`）：
  - 发布话题名在源码硬编码为 `"cmd_vel"`（`controller_server.cpp`），解析为 `/cmd_vel`。
  - 消息类型由参数 `enable_stamped_cmd_vel` 决定（`nav2_util` 的 `TwistPublisher`），默认 true，即发布 `TwistStamped`。

结论：两边消息类型已经一致（都是 `TwistStamped`），只有话题名不同。对齐只需改话题名，在 2.4 接入 nav2 时用 remap 落地：给 nav2 的 `controller_server` 节点加 remap `("cmd_vel", "/diff_drive_controller/cmd_vel")`。2.1 先在 diff_drive_controller 的默认话题上验证底盘闭环。

### 步骤 2：用正确话题和类型验证前进与转向

- 持续发指令：`ros2 topic pub -r 10 /diff_drive_controller/cmd_vel geometry_msgs/msg/TwistStamped "{twist: {linear: {x: 0.2}}}"`。
- 关键：`cmd_vel_timeout: 0.5` 会让单次 `--once` 发布 0.5 秒后速度归零，必须用 `-r` 持续发，否则走走停停。TwistStamped 的 `header.stamp` 可省略（零时间戳时 diff_drive_controller 按当前时间处理）。
- 转向：`twist.angular.z` 设为 0.5，观察底盘原地转，左右轮等速反向。

### 步骤 3：量化验证 odom

- 走直线：发 `twist.linear.x=0.2` 持续 5 秒（理论位移 1m），停后读 `/odom` 的 `pose.pose.position`，与 1m 对比算误差。
- 原地转：发 `twist.angular.z=0.5` 持续约 π 秒（理论转 90°），停后读 `/odom` 的 `pose.pose.orientation`（换算 yaw），与 90° 对比。
- 交叉验证（可选）：用 gz 的模型位姿查询命令（`gz model -h` 查看准确用法）拿 Gazebo 里的真实位移，对比 odom 是否接近。
- 把实测误差记录回报。

### 步骤 4：确认 TF

- `ros2 run tf2_tools view_frames`，确认 `odom → base_footprint` 这条动态 TF 存在且由 `diff_drive_controller` 发布（不是 gz bridge）。
